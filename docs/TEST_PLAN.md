# Test and evidence plan

No application tests were run in Milestone 0 because no application was implemented. The source and environment inspection described in `PROJECT_OVERVIEW.md` was performed; endpoint behavior has not been exercised against a running server.

## Automated tests, when relevant milestones are implemented

- Unit: generated safe paths/filenames; MIME and dimension validation; session/photo transitions; backoff including 429 and jitter; upload idempotency/conflict; template geometry; credential redaction; scope locks.
- Integration: SQLite migrations, atomic-file staging and power-loss recovery simulation; database/filesystem disagreement; camera adapter with fake source; folder importer with partial/duplicate/renamed files; queue restart and server-state reconciliation; API client against a staging-compatible mock; printer adapter with fake spooler.
- E2E: launch packaged app, select event, capture/import with a simulated source, restart, confirm local original and metadata, simulate offline then reconnect, verify one upload to intended album. Cover fullscreen exit, missing camera, low storage and auth expiration.
- Security: hostile IPC origin/payload, traversal and junctions, invalid/oversized image, expired/revoked token, unauthorized event/album, replayed upload, CSP/navigation, packaged secret scan, dependency audit, gallery link scope/revocation.

Use representative fixtures and independent expected results, especially for template output and recovery. Record command, environment, date and artifact/result for every claimed pass. Keep production cloud access out of routine automated testing.

## Manual and physical-hardware matrix

| Capability | Can build/verify without hardware? | Required hardware or service before accepting claim |
| --- | --- | --- |
| Shell, settings, event model, template math, local filesystem, queue logic | Yes, with simulated inputs and offline tests | Windows target PC for installer/fullscreen/performance |
| Webcam preview/capture and permission recovery | API/adapter logic yes | At least one named webcam on target Windows PC |
| Folder import logic | Yes, synthetic file writes | Canon camera + EOS Utility or selected tethering app for workflow claim |
| Direct Canon shutter control | Interface/research only | Licensed SDK, named Canon model, cable, Windows PC |
| Printer layout/queue | Preview and fake adapter | Each supported printer, driver, paper type |
| Cloud upload, album/QR permissions | Mocked contract and offline queue | Staging KOKO API/account and guest device; production access for final controlled release only |
| Offline capture and recovery | Yes, simulated camera and disk/network faults | Full event rehearsal on actual storage and power setup |

## Release gates

Before any real event, pass: installer and rollback check; supported camera and storage write/free-space check; 100+ consecutive capture rehearsal or a sample matching expected event load; restart during save/queue; offline capture and reconnect; integrity scan; event/album correctness and guest access test; operator recovery drill; backup/restore sample; privacy/consent sign-off. Record failed cases and owners. Printing and direct DSLR gates apply only if those features are enabled.

## Hardware-free session check (simulated camera and printer)

`scripts/verify-simulated-session.cjs` drives the packaged app through the real UI: Free claim, storage, event, capture with the simulated camera, review, Finish round, simulated print, then a second launch on the same profile to confirm the session, photo, print job and license are recovered. It proves the software path only; it does not prove any physical camera or printer.

License settings are compiled into the package, so build a throwaway QA package against a local License Server first:

1. Create keys outside the repository: run `node scripts/generate-license-keys.cjs` from a scratch directory.
2. Start the server: `LICENSE_PRIVATE_KEY_FILE=<scratch>/secrets/license-private.pem LICENSE_DB_PATH=<scratch>/lic.sqlite LICENSE_KEY_ID=koko-local-dev-1 node server/license-server.cjs`.
3. Package with `KOKO_LICENSE_API_BASE_URL=http://127.0.0.1:8787`, `KOKO_LICENSE_PRODUCT_ID=koko-photobooth` and `KOKO_LICENSE_TRUSTED_KEYS_JSON={"koko-local-dev-1":"<public key PEM>"}` set, then run `npx electron scripts/verify-simulated-session.cjs "out/KOKO Studio-win32-x64/resources/app.asar" artifacts/sim first` and again with `second`. Keep `KOKO_LICENSE_API_BASE_URL` set when running it.
4. Stop the server and rebuild without those variables before distributing anything; the QA package must never be shipped.

A third phase, `rounds` (set `KOKO_QA_ROUNDS`, default 100), runs a 4-photo round, a retake, a cancel during the countdown and then consecutive single-photo rounds, and checks the session tally, photo count and that no storage recovery is pending.

Results on 2026-11-05 (0.1.29 plus UI changes): `first` and `second` passed; `rounds` with 100 rounds passed in about 45 seconds (104 sessions added: 102 confirmed, 1 retaken, 1 cancelled; 108 photos added; no recovery issues; no renderer errors), and a restart afterwards recovered all of it. Not covered: killing the app in the middle of a round, disk-full, camera unplug, and the video mode.

Fixed after this run: the Free plan no longer attempts a cloud sync that was always rejected (the review banner now says the plan has no online albums), and a cancelled round no longer triggers a rejected `koko:capture-session-finish` call. The script now fails if the Free review banner shows the wrong message; re-run with 30 rounds showed no main-process handler errors. Photos from a retaken round stay in the library.

A fourth phase, `guest`, enters Guest mode (the app resumes Guest mode after a reload, so use a separate profile directory from the other phases) and checks that the preview starts without pressing anything, that operator controls (camera selector, settings button, technical note, sample-session card) are hidden, that the shutter and the Retake/Finish buttons stay inside the viewport in both the ready and review states, and that the next guest starts with no leftover photos. A fifth phase, `guest-sizes` (set `KOKO_QA_LANG` to `th` or `en`), repeats the round at 800x1280 (portrait tablet), 1024x768, 1280x720 and 1920x1080 using Chromium device emulation and fails if the shutter block (disc plus caption), the Retake/Finish buttons or the next guest's ready screen fall below the viewport. Result on 2026-11-05: all four sizes fit in both Thai and English; the tightest margin is about 36px (1920x1080 shutter block ends at 1043). Result on 2026-11-10 after the short-landscape tweak (1366x768 added to the list): all five sizes fit; preview heights 1280x720 = 390px, 1366x768 = 438px; the shutter block ends at 706 of 720 at 1280x720 (about 14px margin, the tightest). A sixth phase, `guest-multi`, runs 4-photo and 2-photo templates in Guest mode at 1280x720 and 800x1280 and checks every photo is taken, the composition is shown, Retake/Finish stay inside the viewport, the next guest starts clean, and the library gains the photos plus one saved composition image. Result on 2026-11-10: all pass after two fixes (an empty frame image no longer makes the capture fail, and Retake/Finish are pinned to the bottom of the screen). A seventh phase, `video`, records a 5s clip in the operator Capture page with the simulated camera and checks the session is confirmed and the stored file is a valid WebM of about 5s (2026-11-10: 5.0s, 830 KB, 1280x720). An eighth phase, `guest-video`, runs a video-clip template in Guest mode (a template option, "Guest captures: Photos / Video clip"; the guest only taps the shutter; the clip length is the default 10s) at 1280x720 and 800x1280: the clip is shown for review, Retake/Finish fit, the session is confirmed with one valid WebM (about 10s) and the next guest starts clean (2026-11-10: pass). Phases `kill-mid-round` then `after-kill` (same profile; set `KOKO_QA_KILL_AFTER` to 1-4 photos) hard-kill the whole process in the middle of a 4-photo round and then restart: the unfinished round must be marked interrupted (or stay in review if all photos were taken), every committed photo must still be in the library, storage must report nothing pending and no bad recovery issues, and a normal round must work afterwards. Result on 2026-11-10: pass at 1, 2, 3 and 4 photos (a kill after the fourth photo leaves the round in `review`, not confirmed, with all 4 photos kept). Killing the process is not the same as a real power cut. Phase `disk-full` simulates a full disk by making file writes fail with ENOSPC (the test script patches `fs.writeFileSync` before the app loads): (1) every write fails from the start, (2) the second photo of a 4-photo round cannot be saved, (3) space is freed and a normal round works. It checks the person sees a clear "storage disk is full" message, no half-saved or temporary files are left (pending recovery 0), saved photos stay readable and the app is not stuck. Result on 2026-11-10: pass after two fixes (a failed index write left a temporary `photo-index.json.*.tmp` that kept the storage in "needs attention"; the raw IPC/ENOSPC text is now replaced by a plain message). Phase `guest-disk-full` covers Guest mode with a 2-photo template whose second photo cannot be saved: the guest sees "Not every photo could be taken. Tap Retake to try again, or ask the staff." (Thai too), Retake/Finish stay on screen, Finish confirms the 1 photo that was saved, the next full round shows no warning and the composition (1280x720 and 800x1280, 2026-11-10: pass). Run it, like every other Guest phase, on a profile that is not already in Guest mode. Not covered: a real full volume, real touch input and the QR state of a plan with cloud albums.
